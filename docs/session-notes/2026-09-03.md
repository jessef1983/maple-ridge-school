## Follow-up (same day)

- Fixed the inline `data:image/...` embed properly this time. Root cause of the earlier failure: the Base64 payload was being hand-transcribed through chat/patch tooling, which silently corrupted long strings. This pass generated the payload directly from image bytes (PowerShell `[Convert]::ToBase64String`) and diffed the embedded string against the source bytes to confirm a byte-exact match before touching anything else.
- Downsized the emblem specifically for signature use: the original `maple-ridge-emblem-original.png` is 1254x1254 (~1MB), far larger than the generator ever displays (max 120px). Resized to 160x160 (~19.6KB PNG, ~26KB Base64) — plenty for retina at signature size, small enough to embed inline without bloating the HTML.
- New asset: `email-signature/maple-ridge-emblem-signature-source.png` (160x160, the resize source for the embedded logo). Deliberately kept out of `images/` and out of `image-manifest.json` — it's an implementation detail of the generator, not a packaged deliverable asset.
- `maple-ridge-staff-signature-generator.html`: replaced the three broken/unused inline-logo constants (`logoSrc`/`embeddedLogoSrc`/`goodLogoSrc` — all mis-typed JPEGs from the failed attempt) and the now-unused `logoSource()` helper with a single correct `const logoSrc='data:image/png;base64,...'`. The actual `<img>` tag in `signatureHtml()` now references `${logoSrc}` instead of the external `../images/...` path, so the SharePoint HTML preview (CSP allows `data:`/`blob:`, blocks external image URLs) should now render the logo. Not yet re-verified in an authenticated SharePoint preview session — do that before calling the preview issue closed.
- Verified: extracted Base64 from the final HTML matches `[Convert]::ToBase64String` of the PNG exactly (diff clean); the inline `<script>` still parses as valid JS.
